
### Design-Pattern

🎨 **Understanding Design Patterns in Software**

A Design Pattern is a proven, reusable solution to commonly recurring problems in software design.
They are not complete code, but templates and best practices that guide you in building flexible, maintainable, and scalable software architectures.

🎯 **_Why We Use Design Patterns ??_**

🗂️ **Establish a Shared Vocabulary**

- Provide a common, high-level language among developers.

- Improves communication:
“We should use a Singleton here.”

🧪 **Promote Proven Solutions**

- Patterns are industry-tested and reliable.

- Prevent rewriting solutions to problems developers solved years ago.

🏗️ **Improve Architecture**

- Enhance flexibility, scalability, and clean structure.

- Enable systems that are easier to extend, refactor, and maintain.

📖 **Increase Readability**

- Recognizable patterns make onboarding easier.

- Improve clarity across large or collaborative codebases.


| 📚 Category                 | 🎯 Purpose                                               | 🧩 Common Examples                                                    |
| --------------------------- | -------------------------------------------------------- | --------------------------------------------------------------------- |
| 🏗️ **Creational Patterns** | Handle object creation in flexible and reusable ways.    | Singleton, Factory Method, Abstract Factory, Builder, Prototype       |
| 🏛️ **Structural Patterns** | Define relations and structure between objects/classes.  | Adapter, Decorator, Facade, Composite, Proxy                          |
| 🤝 **Behavioral Patterns**  | Govern communication and responsibility between objects. | Observer, Strategy, Command, State, Iterator, Chain of Responsibility |


<br><br>
   

| 📌 Topic          | 📝 Description                                                                        |
| ----------------- | ------------------------------------------------------------------------------------- |
| 🧠 **Definition** | Reusable, proven solutions for common software design problems.                       |
| 🎯 **Purpose**    | Structure code in a clean, maintainable, and scalable way.                            |
| 🚀 **Benefits**   | ♻️ Reusable • 🔧 Maintainable • 📈 Scalable • 🗣 Common vocabulary • ✔️ SOLID aligned |

<br><br>

| 🏷️ Pattern             | 🎯 Purpose                                           |
| ----------------------- | ---------------------------------------------------- |
| 🔒 **Singleton**        | Ensures only one instance exists (e.g., DB, Logger). |
| 🏭 **Factory Method**   | Creates objects without exposing creation logic.     |
| 🏢 **Abstract Factory** | Creates families of related objects.                 |
| 🧱 **Builder**          | Builds complex objects step-by-step.                 |
| 🧬 **Prototype**        | Clones preconfigured objects.                        |

<br><br>

| 🏷️ Pattern      | 🎯 Purpose                                                            |
| ---------------- | --------------------------------------------------------------------- |
| 🔌 **Adapter**   | Connects incompatible interfaces.                                     |
| 🎀 **Decorator** | Adds new behavior without modifying existing code.                    |
| 🎛️ **Facade**   | Simplifies complex subsystems behind a unified interface.             |
| 🌳 **Composite** | Represents hierarchical, tree-like object structures.                 |
| 🛡️ **Proxy**    | Placeholder with controlled access (security, caching, lazy loading). |

<br><br>

| 🏷️ Pattern                    | 🎯 Purpose                                                 |
| ------------------------------ | ---------------------------------------------------------- |
| 👀 **Observer**                | Notifies watchers about state changes (LiveData, Streams). |
| 🔄 **Strategy**                | Swaps algorithms at runtime.                               |
| 🧾 **Command**                 | Encapsulates actions as objects (undo/redo).               |
| 🔁 **State**                   | Changes behavior based on internal states.                 |
| 🧩 **Mediator**                | Centralized communication between multiple objects.        |
| 📚 **Iterator**                | Sequentially accesses collection elements.                 |
| 🔗 **Chain of Responsibility** | Passes requests through handlers in a chain.               |

<br><br>

| 🏷️ Pattern      | 🌟 Example                                          |
| ---------------- | --------------------------------------------------- |
| 🔒 **Singleton** | Single system-wide printer manager.                 |
| ☕ **Factory**    | Coffee machine selecting Espresso/Latte/Cappuccino. |
| 🔄 **Strategy**  | Choosing sorting method (QuickSort vs MergeSort).   |
| 🔔 **Observer**  | YouTube subscribers receiving notifications.        |
| 🍕 **Decorator** | Adding toppings to a pizza dynamically.             |
